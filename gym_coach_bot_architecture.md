# Personal Gym Coach — Architecture Specification

## 0. Language Note

This specification is written in English, and the resulting codebase (variable/function names, comments, commit messages, etc.) should also be in English, per normal software convention. This is independent of the product's user-facing language: **every message the bot actually sends to the user, and all bot-side conversational content, must be in Russian** (see Section 11a). Code language and product content language are two different axes — there is no conflict between them.

## 1. Purpose

A single-user Telegram bot that acts as a personal strength + cardio coach across three (extensible) training days — currently chest, back, legs. It replaces an earlier single long-running chat with a general LLM (Gemini web chat), which became unusable once its context grew too large.

Primary goal for the user: fat loss while preserving muscle mass. The bot proposes a workout for the day, negotiates it conversationally, logs what was actually done (strength sets + cardio metrics), and uses that history to inform future sessions and progress reports (Section 3.5). The user's own word is always final; the bot is expected to push back with its own expert opinion when it disagrees, not just comply.

This is a single-user, single-chat, personal project. No multi-tenant concerns.

## 2. Core Design Principle: Why This Doesn't Bloat Like the Old Chat

The previous approach failed because the entire conversation history was replayed to the model indefinitely. This system is built around one structural fix:

**The LLM is stateless. All memory lives in a database, not in chat history.** Before every model call, the application assembles a bounded, purpose-built context from structured data — it does not replay raw conversation history across sessions.

Two tiers of memory:

- **Working (session-scoped) memory** — the live back-and-forth of a single gym visit (plan negotiation, "give me smaller weights," "swap this exercise," discussion after cardio). This is short-lived and exists only to keep one visit's conversation coherent. It is discarded once the session closes. Concretely: every model call made while the session is open includes the full raw conversation so far *for that session* (realistically a few dozen messages, not hundreds) — this is what lets the user talk to the bot like an ordinary chat partner within one visit, referencing anything said a few messages back without re-explaining it. This is not in tension with "no context bloat" (Section 1's original problem): that problem was unbounded growth *across* sessions over months; one visit's own conversation is naturally small and bounded by how long a gym session runs. The "token economy" note in 3.1 step 4 is about the bot's own reply style — not re-narrating the full goal/context recap out loud on every turn — not about withholding earlier messages from the model.
- **Persistent (structured) memory** — lives in the database: goals, injuries, body metrics, per-exercise history and rolling notes, per-split summaries. This is what actually survives between sessions and is reassembled into context on demand.

Critically, **qualitative/narrative memory never accumulates** — each synthesis step overwrites the previous note for a given exercise/split/profile field with a fresh, current one. Only cheap structured numeric history (weight, reps, sets, dates) is retained indefinitely, since storing that is inexpensive and doesn't bloat prompts (it's queried/aggregated, not dumped wholesale into context).

### 2.1 Current date/time

Every context assembly must explicitly inject the current date and time (with the owner's timezone) into the model call. The LLM is stateless and has no inherent sense of elapsed time — without this, date arithmetic that the product depends on (how many days since an injury was last mentioned, Section 5.1; how long since the last weigh-in, Section 8) is unreliable. This is a small detail but a load-bearing one — it was agreed early in design and must not be dropped at implementation.

## 3. Interaction Model

### 3.1 Entry points

All interaction happens via free text in a single Telegram chat, supplemented by inline buttons for structured data entry (see 3.3) and one explicit deterministic command, `/final` (see 3.2). Session close and the show/edit profile mechanism (3.4) are both triggered by recognized free text, not a hardcoded command — see Section 13 for the exact phrasing being deferred to build time. No proactive/unsolicited coaching messages, with exactly two narrow exceptions (see Section 8).

A typical flow:

1. User: "today is leg day" (or similar, free text, may include backstory: poor sleep, missed days, soreness, etc.)
2. Bot assembles context: global profile (current goals, active injuries, body metric trend, training-structure preference, a lightweight cross-split recent-load snapshot) + the legs split's own context (its **active** exercise set by default — Section 4.3 — with their rolling notes, plus its specialization instructions; the fuller archived/historical set is pulled in only on demand, not by default).
3. Bot proposes a plan in free text, stating the current goal(s) briefly (e.g., "optimizing for fat loss while preserving muscle — here's today's plan: ...").
4. User and bot negotiate freely: swap an exercise, argue about weight, etc. During this phase, replies stay lightweight — the bot does not re-paste the full goal/context recap on every turn (token economy).
5. Explicit finalize trigger: either the user says something that clearly signals agreement (e.g., "agreed, give me the final version"), or they use an explicit `/final` command as a guaranteed deterministic trigger. This produces the full structured plan recap and persists it to the database with status `accepted` (awaiting execution). This plan record is NOT dependent on the live chat session staying open — it is durable, so a morning "give me a plan" followed by evening execution (or any gap, even spanning a sleep cycle) works correctly: the pending plan is retrieved from the database regardless of whether working memory expired in between.
6. User does the strength portion; logs results via per-exercise structured buttons (see 3.3).
7. User does the cardio portion (treadmill by default, or an alternative modality — Section 6.4), then reports the heart-rate-monitor readout as free text, using the fields defined in Section 6.4 — this free text is also where any qualitative comment belongs (e.g., "couldn't get my heart rate up today even pushing hard," or the opposite, "zones shot up almost immediately at low effort"), the cardio equivalent of the per-exercise comment in 3.3. No separate button or field is needed for this since cardio reporting is already free text; the synthesis pipeline (Section 5) is what turns it into the cardio fitness rolling note (6.1).
8. Optional short discussion.
9. Explicit session close: either the "Finish workout" button, or a recognized closing phrase (e.g., "that's it for today"). This is distinct from `/final` — `/final` locks the *plan* before the workout; "Finish workout" closes the *entire session* after everything is done and triggers the synthesis pipeline (Section 5).
10. If the user forgets to close the session, there is no background timer forcing it shut. Instead: the next time *any* message arrives (regardless of how much later), the app first checks whether there's a stale open session and, if so, runs the synthesis pipeline on it before processing the new message. This "lazy close" works cleanly with scale-to-zero serverless hosting, which cannot run idle background timers. This ordering also resolves a subtler case cleanly: if that next message is actually an out-of-band body-metric update (Section 6.1) rather than anything training-related, it is still classified correctly, because the stale session has already been fully closed out by the time the new message is handled — there is no window where an open session interferes with an unrelated message's classification.

**Not every message starts or continues a training session.** A standalone message with no relation to an open or new workout — a bare body-metric report ("вес 82"), a goal or injury mention made in passing, a 3.4 show/edit request — is classified as such and applied directly to the relevant persistent field, confirmed via the standard footnote (Section 5's confirmation-footnote policy applies here too, even though no training session is involved). This is a separate, lightweight path from the numbered flow above: the synthesis pipeline (Section 5) specifically processes a *training session's* accumulated free text at close; a standalone out-of-session message is classified and applied immediately, on its own, without ever opening a session.

### 3.2 Finalize command

`/final` (or equivalent recognized phrase) — locks the negotiated plan. Lightweight, deterministic fallback alongside free-text recognition, specifically to avoid the cost/awkwardness of re-stating full context on every negotiation turn.

### 3.3 Structured exercise logging (buttons)

After a plan is finalized, the bot presents inline buttons, one per exercise, for entering the actual result: weight, reps, sets, and a short comment (how it felt, reordering, etc.). A "Done" button finalizes the strength block. Before the whole session is closed, a "Fix" button allows reopening any exercise's entry to correct a misclick. This buttons-for-structured-data / free-text-for-negotiation split was a deliberate choice: free text would get in the way of the negotiation/critique experience the user wants, but is error-prone for exact numbers.

**On-the-spot substitution (e.g., a planned machine turns out broken) gets its own structured entry, not a comment.** If what was actually performed is a genuinely different exercise — not just a lighter weight or an extra set on the *same* one — cramming its weight/reps/sets into the originally-planned exercise's free-text comment would reintroduce exactly the error-prone-numbers problem buttons exist to avoid. Instead: the user reports the swap (free text, same identity-resolution as 4.2 — check the registry, confirm new vs. existing), the bot adds a structured entry for that exercise the same way as any planned one, and the originally-planned exercise is simply marked not done (no sets logged against it), rather than forced to carry the substitute's numbers. This is still a single session with one "Finish workout" close — it's an addition to the structured entries, not a second negotiation round. A substitution driven by external necessity (equipment unavailable) is logged and reacted to neutrally — forward-looking guidance (e.g., noting a muscle-group coverage gap to address next time) if warranted, not criticism of a choice made under constraint; 5.0 already treats this as incidental, not a decision to second-guess the way a negotiated proposal would be.

### 3.4 Show / edit profile — one mechanism, not two

Earlier drafts of this design split this into two separate concepts — a "show my profile" view for data and a separate "dev mode" for behavioral rules — on the theory that data and instructions needed different mechanisms. They don't, not once Section 5.0 (one general rule for how any permanent change gets made) and the hardcoded-core carve-out below both exist: at that point, "data" and "preferences" are just two categories of the same thing — conversationally visible, conversationally editable, confirmed via the same footnote mechanism. Keeping them as two differently-named modes would have been accidental complexity left over from before those two pieces existed.

So there's one mechanism: the user can ask to see any part of what the bot currently holds — training data (goals, injuries and their affected muscle groups, body metric trend, the cardio fitness rolling note, per-split claimed muscle groups and rolling note, the exercise registry with target muscle groups, active/archived status, and each exercise's current rolling note, and the cardio-modality state — current default modality, the treadmill's baseline incline/speed profile and its own rolling note, Section 6.4) or behavioral configuration (tone, coaching assertiveness, each split's specialization text) — and the bot shows it as readable text. Correcting any of it works the same way as any other update: the user states the correction in chat, it's applied, and it's confirmed via the standard footnote (Section 5). When a new split is created, its specialization text is auto-drafted and shown for approval/edit before being saved, same as before — that part didn't depend on there being a separate mode.

**What's genuinely excluded isn't a "mode," it's not data at all.** The hardcoded safety core — the Telegram user-ID check (Section 11), the webhook authenticity/idempotency checks (Section 10.1), and the confirmation-footnote mechanism itself — is never stored as editable state in the first place, so there's nothing for this mechanism to show or change. It's not that these are protected *from* the show/edit mechanism; they were never inside it, because they live in code, not in the profile. "Stop confirming everything, just do it" can adjust how verbose footnotes are (that's a preference); it cannot turn the mechanism off (that was never a setting to begin with).

Retroactive correction of specific past (already-closed) session records is explicitly out of scope (see Section 12) — only current state is editable this way. (This section covers *current state* — goals, injuries, registries, configuration. For analyzing a trend or a slice of raw history rather than showing current state, see 3.5.)

### 3.5 On-demand historical analysis

Separate from both the live default context (3.1, deliberately thin) and the show/edit mechanism (3.4, current-state only), the user can at any time — mid-session or standalone, free text, no special command — ask the bot to analyze a slice of raw history and give a qualitative verdict in prose. Two concrete shapes this takes: reacting to something just logged ("не нравятся мои результаты сегодня, справедливо?" — compare against recent performances of that exercise) and a standalone progress query ("как у меня прогресс за последние 3 месяца?" — summarize a named window). No charts — a prose summary/judgment only, per explicit preference.

- **Scope is resolved from the request itself, not fixed.** The bot infers which exercise(s), cardio modality/profile (e.g. the treadmill's incline/speed trend or the general cardio-fitness/HR-response trend across recent cardio sessions, Section 6.4), muscle group, or split the question is about — from the live session if asked mid-session, or from what's named in the question — and how far back to look: an explicit window if the user names one ("последние 3 месяца"), or a sensible default (the last ~10 performances of the touched exercise) if the request is vague, like reacting to "today." The exact default count/window is a build-time tuning choice (Section 13), not fixed here.
- **It deliberately pulls raw rows, not the rolling note.** This is the one path that bypasses Section 2's "only the current synthesized note, never raw history" default — because the request is explicitly asking for the raw trend, that's the point of asking. It's cheap regardless (Section 2's own reasoning: numeric history is inexpensive to query/aggregate) and is pulled fresh for this one reply only — it's never folded into the standing default context afterward. It also ignores active/archived status (4.3), the same way 4.3's own on-demand pull does: a progress question about an exercise doesn't care whether that exercise is currently in rotation.
- **Read-only — no confirmation footnote.** Unlike the synthesis pipeline (Section 5), this never writes anything; it's an analysis, not a state change, so Section 5's footnote mechanism doesn't apply here.
- **Quality of the verdict is a reasoning question, not a structural one** — whether the model's judgment ("is today's dip fair given the last 10") actually holds up is worth covering in Section 7's empirical validation pass, not assumed to just work by virtue of the data being available.

## 4. Splits as Domain Specialists

- Splits ("training days") are **not hardcoded** — they are a configurable list in the database (default: chest, back, legs), which the user can add to, rename, or retire via ordinary conversation. A retired split is archived, not deleted — its history stays queryable.
- Each split behaves as a domain specialist: it tracks its own exercises and progress, is sensitive to injuries affecting its area, and optimizes within its own domain. This is **not three separate bot personalities** — it's one agent, one chat, one consistent tone, with context *scoped* by which split is active.
- A **global shared layer** is visible to every split regardless of which is active: current goal(s), active injuries, body metric trend, training-structure preference, and a lightweight **"recent load per split" snapshot** (roughly: last trained date + rough volume per split). This lets any split's agent make an informed, responsible decision about e.g. incidentally adding a light exercise from another domain, without needing deep access to that domain's full detailed history/notes.

### 4.1 Muscle groups, not exercise ownership

Earlier drafts of this design gave each exercise a single "owning split" tag. That's wrong, and worth spelling out why: what an exercise targets is a fixed, objective property of the exercise itself (a bicep curl always works the biceps, regardless of which day it's performed on), while how the user organizes those muscle groups into named training days is a subjective, reconfigurable choice. Collapsing those into one mutable "owner" tag per exercise breaks the moment a new split is introduced — e.g., spinning up a dedicated "arms" day would start with zero historical reference data, even though biceps/triceps work has been logged for months under chest/back days.

So the model is split into two parts instead:

- **Exercises carry a set of target muscle groups** (can be more than one — e.g., a bent-over row targets both back and biceps). Assigned once, by the model's own general fitness knowledge, the first time an exercise is introduced (proposed by the bot or named by the user); reused for every later performance of that same exercise, never re-derived. Shown to the user via the standard confirmation footnote so a wrong classification can be corrected. Granularity: everyday fitness vocabulary (chest, back, shoulders, biceps, triceps, quads, hamstrings, glutes, calves, core, forearms, traps, lower back) — not detailed anatomical subdivisions. This also applies during the one-time historical import (Appendix): muscle-group tags are derived automatically from each unique exercise name, the same way as for a brand-new exercise in live use — the import template's "Split" column is only a loose historical label used for date-ordering (Appendix), not a manual muscle-group assignment.
- **Each split has its own configurable list of muscle groups it currently claims** (e.g., Back = lats, rhomboids, biceps; Chest = pecs, triceps). This is the part the user actually organizes and can redefine via ordinary conversation — the same mechanism as changing a goal. Splits are allowed to claim overlapping muscle groups; that's normal, not a bug (e.g., biceps can legitimately get worked from both a back day and a dedicated arms day).

A session does **not** rigidly belong to exactly one split — it's just a dated container that may include exercises touching several different muscle groups (e.g., chest day incidentally includes one back exercise). An exercise's relevance to a given split, at any point in time, is computed as the overlap between the exercise's target muscle groups and whatever muscle groups that split currently claims — never a stored "belongs to split X" fact.

This resolves the scenarios the user raised, without any data migration step:

- **Restructuring** (e.g., splitting a dedicated "arms" day out of chest/back): nothing about any exercise record changes. The user just tells the new "arms" split which muscle groups it now claims (biceps, triceps). Every exercise ever logged that targets those muscles — regardless of which day it was historically performed under — becomes visible, retroactively, as that split's own reference history. A brand-new split is never starting from zero.
- **Partial cross-domain work awareness**: if chest day borrows a back exercise, the back split's agent sees that exercise's recent performance next time it builds its own context (via the muscle-group overlap, not by which day's session it was logged under), and can adjust its own volume target accordingly — without being blindly rigid about hitting a fixed quota (e.g., "5 back exercises") regardless of what's already been covered. This target-flexibility is encoded as guidance in that split's specialization instructions (Section 3.4), not as a hard rule.
- **Negotiating a split's scope into the new default** (e.g., deciding mid-negotiation that back day should now standingly include biceps work, and chest day triceps work): this follows the general explicit-vs-incidental principle (Section 5.0) — a one-off occurrence in a single session does not silently redefine a split's claimed muscle groups; only a clear, explicit statement of intent ("let's make this permanent") does, written with the standard confirmation footnote.

### 4.2 Exercise identity & naming

A real risk with free-text exercise names is silent fragmentation: the same exercise referred to slightly differently on different occasions ("leg press" vs. "жим ногами в тренажёре") could get created as two separate records, splitting its progression history in two. The resolution, matching how the user actually wants to interact:

- **The database always stores the fullest, most specific name** for an exercise. **The bot always proposes using that same specific stored name** when it re-proposes something from history (e.g., repeating last week's plan) — continuity is the bot's responsibility, not something the user needs to get exactly right by memory.
- **During negotiation, the user is expected to reference what the bot just proposed**, not to independently invent fresh terminology. A short reference ("the press," "that thing you gave me") resolves against the small set of items currently on the table (the just-proposed plan), not by fuzzy-matching against the entire historical exercise registry. If the user's shorthand is ambiguous within the current proposal (e.g., two different presses are both on today's plan), the user is expected to disambiguate ("leg press," not just "press") — and the bot should ask rather than guess if it's still unclear which one is meant.
- **If the user does introduce what looks like a new exercise on their own initiative** (not something the bot just proposed) — e.g., naming a substitution during negotiation — the bot checks it against the existing exercise registry for a likely match before creating a brand-new record, and confirms with the user ("is this the same as the leg press you've logged before, or a different exercise?") rather than silently merging or silently duplicating.

### 4.3 Active vs. archived exercises (context scope)

Over time a split will accumulate more exercises than are in current rotation — substitutions tried once, old defaults replaced, one-off variety. Each exercise carries a status: **active** (currently part of that split's regular default set) or **archived** (historical, kept permanently for the record, but not part of the default rotation).

A new exercise defaults to **active** when first introduced *through the normal planning path* — proposed by the bot or explicitly added by the user to the standing rotation. **An exercise created purely as an on-the-spot incidental substitution (3.3, 5.0's own "equipment unavailable" example) defaults to archived instead** — it still gets its own registry record and performance history from day one (4.2), but doesn't silently join the split's standing default rotation off the back of a single necessity-driven event that was never a standing statement. It only becomes active the normal way: an explicit, permanent statement from the user (5.0) during a later negotiation.

The transition to **archived** is not a separate mechanism to build — it piggybacks on the explicit-permanent-change event that already exists (Section 5.0): whenever the user explicitly and permanently takes an exercise out of a split's default rotation — whether it's being swapped for a specific replacement, or simply dropped with no replacement in mind (e.g., "let's just stop doing lunges, no need to add anything in its place") — that exercise flips to archived; if a replacement was named, the incoming one becomes active. There is no time-based auto-archiving and no separate "retire this" command needed — the status simply tracks the split's current explicit default set at all times.

This status governs what gets pulled into context by default, which is a second, independent axis of the "don't bloat the context" principle (Section 2) — bloat from *breadth* of accumulated exercises over time, not just from raw chat history:

- The common case — "same split as last time, just continue" — only needs the **current active set** for that split (a small, bounded list matching the training-structure preference, Section 6.1) plus their rolling notes. This is what gets assembled by default.
- The fuller historical set (including archived exercises, matched via the muscle-group overlap regardless of active/archived status) is pulled in only on demand: the user explicitly asks for variety/new ideas, asks what they used to do for something, or a split is newly created/reconfigured (Section 4.1's restructuring case, where pulling in *all* matching history — active or archived — is exactly the point).

## 5. Synthesis Pipeline (Session Close)

Triggered on explicit close or lazily on the next message after a stale open session is detected. In a single step, the full free-text content of the session (not just the button-logged structured data) is scanned and used to:

- Update each touched exercise's rolling note — a short, current synthesized takeaway (not raw comment text) that carries forward the concrete last working weight/reps/sets (Section 6.3 — this note is the agent's only default source for "what number to propose next," since raw history isn't pulled by default), plus situational modifiers (e.g., "performed first instead of planned second, while fresh — felt easy; don't rush to raise the weight, may be an ordering effect"). **When a result is explained by a clearly stated one-off external cause** (poor sleep, a missed week, not having eaten — Section 5.0's incidental case) rather than genuine progress or regression, the note should say so explicitly and anchor the next proposal to the established trend, not to the anomalous session — e.g., a weak result explained by poor sleep should read as "stayed at the established working weight; this session's dip was sleep-related, not a regression" rather than quietly becoming the new baseline for next time.
- Update the session's primary split's rolling note (6.4) — only that one split, even if exercises touching other splits' muscle groups were incidentally logged too (4.1); those exercises' own rolling notes still update per the bullet above.
- Update the global profile: general state (sleep, soreness, mood, missed days), the cardio fitness rolling note (6.1, from any qualitative comment in the cardio report — Section 3.1 step 7), goal changes, injury creation/resolution, body-metric mentions if any.
- Persist all numeric results (weight/reps/sets, cardio metrics) permanently — cheap, never pruned.
- Clear the session's raw working memory.

**Every silent write this pipeline makes to persistent profile/data is accompanied by a short confirmation note appended to the bot's reply** (e.g., "Noted: marked the knee injury as resolved as of Oct 1"), which the user can correct with their next message. This confirmation-footnote policy is universal — it applies to every category of automatic write (injuries, goals, exercise defaults, etc.), not just injuries. When a single session close touches several fields at once (an exercise note, a goal mention, an injury update), these should read as one short consolidated note, not a stacked list of separate confirmation lines — exact presentation is left to be worked out in practice at build time, not specified here.

### 5.0 General principle: explicit vs. incidental changes

This single principle governs several places in this document, so it's stated once here rather than repeated: a default only changes permanently on a **clear, explicit statement of intent** from the user. Anything that happens just once, incidentally, in the course of a session — swapping an exercise because the equipment was busy, doing one extra set, mentioning a muscle group in passing — is scoped to that session only and leaves no standing default changed. This applies uniformly to: a split's claimed muscle groups (Section 4.1), an exercise's archived-vs-active transition (Section 4.3), and exercise substitutions generally (Section 5.1 covers the injury-linked case specifically). Every permanent change made this way still goes through the standard confirmation footnote above.

### 5.1 Injury handling specifically

- Like exercises (Section 4.1), an injury carries a set of **affected muscle groups/body areas**, assigned the same way (the model's own judgment when the injury is first mentioned, same granularity vocabulary, correctable via the confirmation footnote). This is what actually scopes an injury to the right split(s) — via the same overlap logic as muscle groups generally — instead of a flat list that either bleeds into every split's context indiscriminately or fails to surface in the one split where it actually matters (e.g., a knee injury should be prominent in the legs context, not generically present everywhere).
- An injury becomes "resolved" only when detected from an explicit or implicit statement in conversation (e.g., "knee hasn't hurt in 3 days") — never assumed by the model on its own, since the LLM has no persistent memory; this detection-and-write is the application's job.
- Because the user won't reliably remember to ever say "it's resolved," there's a soft backstop: if an injury hasn't been mentioned/reinforced for roughly a month, the bot should proactively ask about it the next time it's contextually relevant ("you mentioned an elbow issue about a month ago — still relevant?") rather than either holding it active forever or silently dropping it.
- A substitution tied explicitly to a stated injury in the conversation is treated as **temporary**, linked to that injury, and should be proposed to revert once the injury resolves (an exception to 5.0's general rule — this one *is* time-bound, to the injury's own resolution, rather than needing a separate explicit statement to undo). This isn't limited to strength exercises — the same reasoning applies to swapping the treadmill for an elliptical when a leg/knee injury makes it relevant (Section 6.4): an injury's affected muscle groups/body areas are exactly what should prompt the bot to suggest a cardio-modality substitution too, not just a strength one.

## 6. Data Model (High-Level Entities)

Exact schema (column types, indexes, etc.) is left to implementation. This section lists the entities and relationships that need to exist; it is a contract for what must be representable, not a literal DDL.

**Initial state.** There is no onboarding interview. The database ships pre-seeded with the defaults already settled in this document: the three default splits (chest, back, legs) with sensible default claimed muscle groups, the default training-structure preference (6.1), and the stated goal (fat loss while preserving muscle, Section 1). The user refines any of this through ordinary conversation from the first message onward — nothing needs to be configured before the bot is usable. Creating a new split later (Section 4.1's restructuring case) should bundle naming it and assigning its claimed muscle groups into the same step/exchange — a split should never exist in an intermediate state where it has no muscle groups claimed yet.

### 6.1 Profile (global, single row conceptually)
- Current goal(s) — a list, mutable via conversation, recapped briefly at the start of every plan proposal.
- Training-structure preference — mutable, default: 3 primary exercises (normal rest between sets) + 2 secondary/accessory exercises performed as a superset with no rest between them; target total session time ≈ 2 hours (≈1h strength + ≈1h cardio, treadmill by default — Section 6.4). This default is global, but any split can carry its own override (same mutability mechanism, same explicit-vs-incidental rule, Section 5.0) that takes precedence over the global default for that split specifically. This matters concretely for a split like a dedicated arms day (Section 4.1's own example), which plausibly doesn't need the same 3+2 shape as a full day — without a per-split override, the only way to change that would be changing the shape for every split at once.
- General state — a rolling (overwritten, not accumulating) summary: sleep, soreness, mood, recent missed days, etc.
- **Cardio fitness rolling note** — a short synthesized takeaway on how responsive the user's heart rate currently is to effort (e.g., "recently needs noticeably more effort to reach target zones" / "zones come up almost immediately even at low effort"), overwritten each time, same shape and treatment as every other rolling note in this document (6.2's split note, 6.3's exercise note, 6.4's treadmill-profile note). This is global rather than attached to a specific modality or split: cardio happens at the end of every session regardless of which split it followed (3.1 step 7), on whichever modality (treadmill or elliptical, 6.4) — the thing being tracked here is the user's own cardiovascular conditioning, not a machine setting, so it doesn't belong to the treadmill's own profile note (which tracks incline/speed progression specifically) or to any one split.
- Active injuries — each with status (active/resolved), resolution date, affected muscle groups/body area (see 5.1), and the soft-decay check described in 5.1.
- Body metrics — timestamped entries (weight in kg, muscle mass in kg, body fat in % — matching exactly what the user's own scale app reports; not all three are necessarily the same unit type, and the schema must not assume otherwise), logged independently of any training session, at any time.

### 6.2 Splits
- id, display name, status (active/archived), specialization instructions (free text, user-authored behavioral guidance — tone, priorities — editable conversationally via Section 3.4's mechanism, auto-drafted on creation and shown for approval).
- **Claimed muscle groups** — a list, mutable via conversation (see 4.1). This is what actually determines which exercises' history shows up as this split's own reference, via overlap with each exercise's target muscle groups (6.3) — not a stored link to specific exercises.
- Rolling "current note" — the split-level equivalent of an exercise's rolling note (6.3): a short synthesized takeaway on how the split is trending overall, overwritten each time by the synthesis pipeline (Section 5's "update the session's primary split's rolling note"), never accumulated. This is a separate field from specialization instructions above — one is the user's own standing configuration, the other is the pipeline's own running synthesis; conflating them into a single "summary" field, as earlier drafts implicitly did, would mean the pipeline silently overwriting text the user explicitly authored and approved.

### 6.3 Exercises
- id, name (see 4.2 for naming/identity resolution).
- **Target muscle groups** — a list (an exercise can target more than one), assigned once by the model's own fitness knowledge when the exercise is first introduced, reused thereafter, correctable via the confirmation footnote. This is a property of the exercise itself and is not split-specific (see 4.1) — it does not change when the user reorganizes their splits.
- **Status** — active or archived (see 4.3). Governs default context scope, not visibility in the permanent record. Note: this is a different concept from a split's own active/archived status (6.2, meaning "retired or not") — same vocabulary, two unrelated entities.
- Rolling "current note" — latest synthesized qualitative takeaway, overwritten each time, never accumulated. **This must carry forward enough concrete detail — at minimum the last working weight/reps/sets — that the agent can propose today's numbers from this note alone.** The default context (3.1 step 2, 4.3) never pulls raw performance history automatically; this note is the only thing standing in for it in the common case, so a purely vague trend sentence with no concrete number isn't sufficient.
- Performance history — one row per time performed: date, weight, reps, sets. Cheap, kept indefinitely, never pruned or summarized away (only the narrative note is kept current-only).

### 6.4 Sessions
- date, status (open/closed), free-form container linking the strength results, the cardio record, and (only while open) the raw working conversation for that visit.
- **Primary split** — which split this session was conducted under (the one named in the opening message, e.g. "today is leg day," Section 3.1 steps 1-2). This exists precisely because Section 4.1 deliberately does *not* make a session belong to exactly one split by data ownership — but synthesis (Section 5) still needs a single, unambiguous split whose rolling note it updates, and context assembly (3.1 step 2) needs a single split to scope its default context to. An exercise touched this session that belongs to a *different* split via muscle-group overlap (4.1's cross-domain borrowing) still gets its own rolling note updated (Section 5's first bullet) — that doesn't trigger an update to any other split's rolling note; the other split picks up the change naturally through its own overlap lookup next time it builds context, exactly as 4.1's "partial cross-domain work awareness" already describes.
- Plan sub-record: status (proposed → accepted/awaiting execution → **fulfilled or abandoned**), the agreed exercise set at finalize time. A plan that was accepted but never executed must not be left dangling indefinitely: when its session gets closed (explicitly or via the lazy-close check, Section 3.1 step 10) without any results ever having been logged against it, the synthesis pipeline (Section 5) marks the plan `abandoned` rather than leaving it stuck at "awaiting execution." A session that closes this way — talk but no logged results — is otherwise a no-op for the synthesis pipeline: there's nothing to update beyond this plan-status cleanup. The complementary transition, `accepted` → `fulfilled`, is the default on session close whenever at least one result was logged against the plan — logging every planned exercise is not required for this status; a session that did three of five planned exercises and then closed is `fulfilled`, not left in limbo, since the product's general stance is to record what actually happened rather than enforce the plan exactly (Section 3.3's "any substitution made on the spot" already assumes deviation from plan is normal).
- Cardio record (per session, all manually typed by the user from their heart-rate-monitor app, no image/vision parsing in production): duration, time spent in each of heart-rate zones 1–5, total calories, % calories from carbs / protein / fat, plus:
  - **Modality** — which cardio machine this session used. Defaults to the treadmill; a swap to an alternative (e.g., an elliptical) follows the exact same explicit-vs-incidental and injury-linked rules as a strength exercise substitution (Sections 5.0/5.1) — tied to a stated injury, it's temporary and reverts once that injury resolves; stated as a standing preference change, it's permanent; mentioned once in passing, it's scoped to that session only.
  - **Treadmill profile** (meaningful only when modality = treadmill) — the user's hill/foothill incline-and-speed interval pattern, logged as a short list of incline/speed pairs with no per-interval timing (not needed). This has the same two-level shape as an exercise: a baseline profile that only changes permanently on an explicit statement (Section 5.0), plus a rolling note tracking how it's trending (steeper/faster over time, same idea as an exercise's rolling note, 6.3) — and each session separately logs the actual incline/speed values used that day, which may match the baseline or deviate from it incidentally without redefining it, the same way a logged set's weight can differ from an exercise's usual working weight without changing the default.
  - **Elliptical** (the modality's own structured field, meaningful only when modality = elliptical): **difficulty/resistance level** — a single per-session value, logged the same way reps or weight is (kept indefinitely as numeric history, Section 2). Unlike the treadmill, there's no separate baseline-profile-plus-rolling-note layer defined for this yet, since the elliptical is only ever a temporary stand-in during a leg/knee injury (5.1) rather than a modality the user trains on in its own right — heart-rate zones (already generic, above) are what the user actually watches on it. If that changes and trend-tracking on difficulty becomes wanted, it's the same additive step as the treadmill's profile — not a redesign.

  (Vision-based screenshot parsing was considered and rejected as unreliable for this use — numbers that only appear as bar height or line position, without a printed value, are not something a vision model should be trusted to read accurately for a metric the user wants to actually act on.)

## 7. LLM Integration

- **Provider/model**: default working assumption is a Gemini Flash-tier model; a comparable alternative (e.g., an OpenAI "mini"-tier model) was also considered. Final provider/model selection is deferred to build time, since model lineups and pricing change quickly. The deciding principle: **favor reasoning/instruction-following quality over minimizing cost.** At this project's actual volume (roughly 13 sessions/month × ~25 messages ≈ 325 model calls/month), even a materially stronger/pricier model tier costs on the order of a few dollars a month — not meaningfully different from the cheapest tier, which is worse at the nuanced cross-session reasoning this product depends on (progressive overload judgment, cross-split load awareness, injury-aware adjustments). Do not optimize for the free tier specifically — Google no longer reliably publishes free-tier numbers, and chasing it isn't worth the quality trade-off.
- **Combined vs. separate calls — an open question to validate, not a fixed requirement.** A single combined call (reply + structured extraction in one structured-output generation) halves API usage versus two separate calls — but at this project's volume the dollar savings are negligible (see the pricing estimate in the point above), while structured-output mode can measurably degrade a model's free-form reasoning quality, which matters more here than the cost does (the user's explicit priority is coaching judgment, not spend). Don't hardwire the combined approach by default; validate it empirically at build time:
  1. Write both variants of the message handler (one combined structured-output call; one plain conversational call plus a separate extraction call).
  2. Run the same ~10-20 scripted representative exchanges through both (a plan proposal, a pushback/renegotiation, an exercise swap, a session with an injury-linked substitution, a session close touching several fields at once, an explicit-vs-incidental pair — an in-the-moment emotional comment, e.g. "ugh, hate this exercise, never again," against a deliberately explicit permanent statement made during negotiation, e.g. "let's permanently replace this with X," to confirm the model doesn't treat the former as triggering a default change — an on-demand historical-analysis request (Section 3.5), e.g. feeding it ~10 real logged rows for one exercise and checking whether its "is today's dip fair" verdict is actually sound against those numbers, not just plausible-sounding — and a three-session noise-discounting sequence for one exercise within a single split: a strong result explained by a rested week, a weak result explained by poor sleep/a missed meal, then a normal result, checking whether the resulting rolling note (6.3) and the next session's proposed weight correctly anchor to the established/normal trend rather than treating the poor-sleep session as a new baseline or averaging it in).
  3. Judge each variant on two axes: does the conversational reply still read like a confident, expert trainer willing to push back (subjective — the user is the actual judge here, since it's his read that matters), and does the structured extraction come out correct against what was actually said (objective — check it against the expected values for each scripted exchange).
  4. Use whichever variant holds up on both; if combined is just as good, it's simpler and marginally cheaper — if it visibly degrades the conversation, use separate calls, since the cost difference doesn't justify the trade-off.
- **Billing**: enable auto-recharge/pay-as-you-go if the provider supports it (note: as of 2026 Gemini API billing has been trending toward requiring prepaid credit for new accounts — verify the exact current mechanism at setup time). Set a generous spend cap (e.g., $10–15/month) as a safety ceiling against bugs/anomalies, not as an expected operating limit.
- **Graceful failure**: any API, billing, or quota error must produce a clear, immediate message to the user (e.g., "couldn't reach the model, check the API balance") rather than silently failing or hanging — especially important since the user may be mid-workout with no patience for debugging.

## 8. Scheduled Jobs (The Two Deliberate Exceptions to "Reactive Only")

The bot does not initiate conversation on its own, with exactly two narrow, explicitly scoped exceptions — both implemented via one external scheduler (e.g., Cloud Scheduler) hitting an HTTP endpoint on a recurring schedule, since a scale-to-zero serverless host cannot run its own idle background timers. ("Initiate" specifically means sending a message the user didn't prompt at all — reaching out of nowhere. It does not cover the bot volunteering a related aside inside a reply to something the user already said, such as the injury soft-decay check-in in Section 5.1 — that only ever rides along on a reply the user's own message already triggered, so it's proactive in tone but reactive in trigger, not a third exception to the rule below.)

1. **Weigh-in reminder** — checked weekly; only sends a nudge if no body-metric entry has been logged in the last 7 days (not sent unconditionally — avoids nagging when the user already logged recently).
2. **Backup export** — see Section 9.

No other proactive behavior is in scope. This was a deliberate, narrow carve-out from the "no initiative" decision, not a reopening of it.

## 9. Storage & Backup

- **Database**: Postgres via Supabase (free tier).
- **Backup**: the same weekly scheduled trigger as the weigh-in reminder also exports all persistent data — this must match Section 2's own definition of what persistent memory contains, not just the numeric/structural part of it: profile (goals, injuries, body metrics, the current rolling general-state summary, and the cardio fitness rolling note), the split registry (claimed muscle groups, status, specialization instructions, and each split's current rolling note), the exercise registry (target muscle groups, active/archived status, and each exercise's current rolling note), the cardio-modality state (current default modality, the treadmill's baseline incline/speed profile, and its own rolling note — Section 6.4), and the full performance history — both strength (weight/reps/sets per exercise) and cardio (duration, HR zones, calories, macros, modality, logged incline/speed actuals for the treadmill, and logged difficulty level for the elliptical, per session) — to a file and sends it to the user as a Telegram document — landing in their own chat/device as an informal personal copy, with no additional storage infrastructure needed. Estimated data volume stays small (low single-digit MB even after years of 3x/week use), so file size is a non-issue at any reasonable frequency.
- Verify Supabase's free-tier backup retention at build time as a secondary safety net; the Telegram-delivered export is the primary one regardless.
- Given the backup cadence and small realistic data volume, worst-case data loss in a catastrophic failure is bounded to roughly the most recent week — acceptable for a hobby project, especially since recent sessions also remain visible in the Telegram chat history itself.

## 10. Hosting & Infrastructure

- **Interface**: Telegram Bot API via webhook. Standard Telegram bot account — Telegram Premium is not required; the Bot API is free regardless of the owner's personal Telegram plan.
- **Compute**: serverless (e.g., Google Cloud Run), scale-to-zero when idle. Wakes on an incoming webhook message within a couple of seconds — no manual "turn the bot on" step needed. Accepted latency tolerance: up to ~20 seconds end-to-end for the first message after idle (cold start + model generation) is acceptable; beyond that is worth investigating, not before.
- **Message processing**: sequential per chat (avoid processing two messages concurrently and racing on state) — cheap to guarantee and worth doing regardless of the fact that, given how the user actually writes (long single messages, not rapid-fire), the risk is low in practice.

### 10.1 Webhook reliability

Two gaps worth closing explicitly, since they're easy to miss in exactly this serverless-webhook shape and cheap to build in from the start rather than patch later:

- **Authenticity**: the webhook endpoint must verify Telegram's `secret_token` header (set when registering the webhook), not just check the sender's user ID inside the message payload (Section 11). Checking only the payload content means anyone who discovers the endpoint URL could POST a forged update claiming to be the owner; the secret token proves the request genuinely came from Telegram.
- **Idempotency**: Telegram may redeliver the same update if it doesn't get a fast enough acknowledgment — a real risk here specifically because cold start + a model call can push response time close to Telegram's retry window. The handler must dedupe by Telegram's `update_id` so a redelivered update doesn't get processed twice (e.g., double-logging a set, double-triggering session close).

## 11. Security

- Single-user only. The bot must check the sender's Telegram user ID against the owner's known ID and ignore/reject messages from anyone else — this is personal health data. Multi-user support is out of scope; if ever revisited, treat it as a materially different project, not an incremental extension.
- This user-ID check alone only validates the payload's claimed content, not that the request genuinely came from Telegram — see Section 10.1 for webhook-level authenticity verification, which is the actual security boundary.

## 11a. Language

All bot-facing content — every message the bot sends, plan proposals, confirmations, the profile/instructions views — must be in Russian. This is the language the owner actually uses day to day; it is unrelated to the codebase's own language (see Section 0).

## 12. Explicitly Out of Scope

- **Nutrition/calorie tracking.** The user manages diet independently; the bot reasons only about training stimulus, not caloric intake.
- **Automatic integration with the user's scale (Xiaomi) or heart-rate-monitor app (Polar) APIs.** No official/stable API exists for reliable use here; all body metrics and cardio metrics are entered manually as text by the user, read directly off those apps' own screens.
- **Retroactive correction of specific historical (already-closed) session records.** The user explicitly doesn't need this — by the time an error would be noticed, they won't recall the correct value anyway. Only current state (Section 3.4) is editable conversationally.
- **Multi-user support.**
- **General proactive coaching/initiative** beyond the two narrow scheduled exceptions in Section 8 — meaning the bot never sends a message the user didn't prompt at all, outside those two jobs. This does not restrict an aside volunteered inside a reply the user's own message already triggered (see Section 8's clarification); Section 5.1's injury check-in is exactly such an aside, not a third exception.

## 13. Deferred to Build Time (Not Architectural Blockers)

These are intentionally left open — they're implementation tuning, not product-shape decisions, and the answer may depend on what's current when building starts:

- Exact "how long is a session considered stale" threshold for the lazy-close check (Section 3.1, step 10).
- Exact default lookback window/count for on-demand historical analysis when the user doesn't name one (Section 3.5) — "~10 performances" is a reasonable starting point, not a fixed spec.
- Exact structured shape for logging the treadmill's incline/speed interval pairs (Section 6.4) — how many intervals, field naming — is a build-time schema detail, not fixed here.
- Final LLM provider/model name and version (Section 7).
- Exact current Gemini API billing mechanism (prepaid vs. postpaid/auto-recharge) — verify directly when setting up the API key.
- Supabase free-tier backup retention specifics.
- Exact trigger phrasing/command names beyond `/final` (e.g., the literal command or phrase for asking the bot to show its current data or configuration, Section 3.4).
- Full column-level database schema.
- **Specific vendor/library names are defaults, not hard requirements.** "Google Cloud Run" and "Supabase" are named throughout this document because they're a sensible, cheap, well-documented fit for the stated properties (serverless/scale-to-zero compute, a Postgres-compatible relational database) — not because the product depends on that specific brand. Any equivalent that satisfies the same properties (scale-to-zero, wakes on webhook, free/cheap Postgres hosting) is an acceptable substitution at build time. The same applies to the Telegram bot library, the Gemini/LLM SDK, and the scheduler used for Section 8's jobs — pick whatever's current and well-supported when building starts. What *is* load-bearing and should not be substituted away are the architectural properties themselves: a stateless LLM called with app-assembled context (Section 2), and no reliance on a background timer for the lazy-close mechanism (Section 3.1). Whether message handling uses one combined call or two separate calls (Section 7) is explicitly *not* in this load-bearing set — it's an empirical build-time choice, not a fixed property.

## Appendix: One-Time Historical Data Import (Pre-Launch Script — Not Part of the Live Bot)

**This is deliberately outside the numbered architecture above.** Everything in Sections 1–13 is the product: code Claude Code builds and the owner keeps running. This appendix describes a separate, throwaway script — run once against the database before the bot's first real session, then discarded. It is not a bot feature, has no Telegram-facing surface, is not deployed alongside the live service, and is not something the live product needs to expose, maintain, or ever run again. An implementer should not build this as part of the bot's own codebase/API — a local one-off script that writes directly to the database is sufficient, and preferable, since nothing here needs to survive past the one run.

- **Not based on fetching a shared Gemini chat link** — that's an authenticated Google product page this system has no reliable way to read, and even if it could, free-text extraction over a large unreviewed import is more error-prone than the user wants for a one-time bulk load.
- **Source**: the user transcribes a handful of his most recent sessions per split from his existing Gemini conversation into a structured spreadsheet (template provided separately, see companion file). **There's no hard minimum, and "15-20 total / ~5 per split" was only ever a rough starting suggestion, not a derived requirement.** The import's actual job is to seed each exercise's rolling note (6.3) with one concrete, recent reference point instead of starting the bot from zero — 2-3 recent sessions per split, each with at least a short comment, already does that; the note only ever carries the *current* state forward, not depth. More sessions mainly widen Section 3.5's on-demand analysis lookback before enough live sessions accumulate on their own (which happens within a few weeks at 3x/week) — a real but fast-decaying benefit, not a requirement. If the first few transcribed sessions already feel representative, stopping there is a reasonable call, not a shortcut that breaks anything.
- **Purely numeric/structural fields** (weights, reps, sets, cardio zone times, calories, macros, modality, treadmill incline/speed actuals, elliptical difficulty) are loaded directly into the database with no model call — same as originally specified.
- **Muscle-group tagging is not model-free, and that's fine.** Per 4.1, an exercise's target muscle groups are assigned "by the model's own general fitness knowledge" — that's an LLM call, not a lookup table, in live use too. The import script does the same thing: one short classification call per *unique exercise name* in the sheet (not per row — the same name repeated across several session-order rows is tagged once and reused, exactly as 4.1 already specifies for any exercise's whole lifetime). For a 15-20-row import with the usual handful of distinct exercises, that's maybe 5-10 calls, not 15-20.
- **Free-text comment columns are not left as inert reference text.** The template's comment columns (strength's "Comment / how it felt," cardio's comment field — Section 6.4) are run through the *exact same* per-entity synthesis step the live pipeline uses (Section 5: current note + one new raw comment → one new overwritten note) — once per comment-bearing row, grouped by entity and replayed in the template's session order (e.g., all of one exercise's comments, oldest to newest, each call building on the last). This is a sequential replay, not a bulk digest: if an exercise has three historical comments, the script calls the same synthesis step three times in a row, exactly as if those three sessions had been logged live one after another. The result is a rolling note indistinguishable from one the live bot would have produced itself — so the bot behaves as designed from its very first real session, with no "seed the note manually" step left for the user to remember. This reuses Section 5's existing synthesis logic as-is; it does not require inventing a new "summarize many comments at once" capability.
- **Implication**: unlike the structured-field copy above (genuinely model-free), both muscle-group tagging and comment synthesis need LLM access — together, on the order of 15-25 short calls total for a 15-20-row import (a handful of unique exercises tagged once each, plus one call per comment-bearing row). That's a one-time cost paid by the script before the bot ever goes live, not a standing feature of the deployed bot.
- **Dates**: exact historical dates are not known. The template assumes roughly one week of spacing between consecutive sessions of the *same* muscle group as a simplifying placeholder for ordering; this is an approximation, not real data, and should be treated as such.
- **Post-import review**: after the script runs, the user should still do one pass through "show my profile" (Section 3.4) to sanity-check what loaded — and this pass must explicitly include setting each imported exercise's status (Section 4.3) to active or archived. Imported rows have no natural default here: marking everything "active" would immediately refill the default context with discontinued exercises, recreating the exact bloat-by-breadth problem Section 4.3 exists to prevent, right at the start of the product's life. This status check is not optional cleanup — it's part of what makes the import usable day one. (The rolling notes themselves, per the point above, no longer need seeding during this pass — only the active/archived call does.)
